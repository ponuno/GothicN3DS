# Gothic 3DS — база порта

Основа для запуска мира Gothic 1 на New Nintendo 3DS: конвертер ресурсов на ПК, формат данных под PICA200 и рантайм, в котором по мирам игры можно ходить, плавать и переходить из одного в другой. Это этапы 0–2 плана; игровой логики, персонажей и звука здесь ещё нет.

Данные игры в репозиторий не входят и не распространяются: конвертер читает вашу установленную копию.

![Тестовая сцена в ПК-сборке рантайма: лагерь днём, озеро, пещера с бассейном и лестницей, ворота на закате](docs/preview.png)

## Что внутри

| Часть | Каталог | Назначение |
|---|---|---|
| Конвертер `g3ds-bake` | `tools/` | Читает миры, лайтмапы, объекты (меши, модели, декали), порталы и текстуры из VDF через ZenKit, пишет `data.pak` |
| Ядро | `core/` | Форматы архива, текстур и чанков мира; общие для ПК и консоли |
| Движок | `engine/` | Фоновая подгрузка чанков, отсечение, регулятор нагрузки, столкновения, ходьба, плавание, лестницы, вода, небо и время суток, переходы между мирами |
| Бэкенд 3DS | `platform/3ds/` | libctru + citro3d, вершинный шейдер PICA |
| Бэкенд ПК `g3ds-host` | `platform/host/` | Программный рендер 400×240 с тем же конвейером, для отладки без консоли |
| Тесты | `tests/` | Модульные и сквозные, включая импорт из форматов ZenGin и проверку бэкенда 3DS на имитации citro3d |

Рантайм (`core`, `engine`, `platform`) написан на C++17 без STL, исключений и RTTI. Инструменты — C++20, этого требует ZenKit.

## Сборка на ПК

Нужны CMake 3.16+, компилятор с C++20 и git. ZenKit скачивается при настройке.

```sh
cmake -S . -B build
cmake --build build -j
ctest --test-dir build --output-on-failure
```

Проверка всей цепочки на встроенной тестовой сцене, игра не нужна:

```sh
./build/g3ds-bake synth -o data.pak
./build/g3ds-host --pak data.pak --frames 300 --shots 4 --out frame
```

`g3ds-host` пролетает камерой по миру, сохраняет кадры в PNG и печатает статистику: треугольники и вызовы отрисовки на кадр, занятую память, перерисовку. Тестовая сцена состоит из двух миров: долины с лагерем и пещеры, куда ведут ворота рядом со стартом (`--world cave` открывает пещеру сразу).

## Запекание миров Gothic

```sh
./build/g3ds-bake world --game "/путь/к/Gothic" -o data.pak
./build/g3ds-bake info data.pak
./build/g3ds-host --pak data.pak --still --shots 1 --out world
```

Конвертер начинает с `WORLD.ZEN` и сам запекает миры, в которые из него ведут триггеры смены уровня (шахты, храм). Всё попадает в один `data.pak`, текстуры у миров общие.

Что переносится из игры:

- меш мира со светом вершин и светом лайтмапов;
- объекты: меши `.3DS`, модели `.MDS`/`.ASC` в позе покоя (сундуки, кровати, двери), морф-меши `.MMS`, декали;
- вода: полупрозрачная, с анимацией кадров текстуры и прокруткой;
- триггеры смены уровня и точки прибытия, лестницы, признак подземного мира.

Частицы (костры, факелы) и спрайты, повёрнутые к камере, пока пропускаются; конвертер пишет их число. Двери и ворота рисуются, но не мешают пройти: открывать их ещё нечем.

Полезные параметры: `--zen OLDMINE.ZEN` (начать с другого мира; можно указать несколько), `--no-follow` (не запекать миры за порталами), `--chunk 4000` (размер чанка в см), `--max-tex 128` (длинная сторона текстуры), `--quality 0|1|2` (качество ETC1), `--no-objects` (только ландшафт), `--no-lightmaps` (не запекать свет помещений), `--flip` (перевернуть порядок обхода вершин), `--seal 0.5` (на каком расстоянии в см заделывать швы между полигонами), `--no-seal` (не заделывать), `--step 0.125` (шаг координат вершин в см).

У `g3ds-host` три режима: пролёт над миром (по умолчанию), `--walk` (ходьба по земле со столкновениями) и `--still` (неподвижный вид). `--world oldmine` выбирает мир, `--cam X,Y,Z,YAW,PITCH` — точку и направление взгляда, `--time 19.5` — время суток, `--detail 7000,3500` — дальность прорисовки средних и мелких объектов, `--stream sync|inline|thread` — как подгружаются чанки на ходу (`thread` — фоновым потоком, как на консоли).

Место с консоли можно открыть на ПК: строка `pos` на нижнем экране даёт координаты, например `--cam -1619,-1300,-4743,0,0 --still --shots 1`. Программный рендер закрашивает пиксели по тем же правилам, что и видеочип, поэтому щель в геометрии видна и в нём.

Конвертер проверяет себя и пишет результат в отчёт (`g3ds-bake info data.pak` печатает его снова):

| Строка отчёта | Что должно быть |
|---|---|
| `winding check` | больше 60% площади смотрит вверх; для подземного мира проверка ничего не говорит, и отчёт это отмечает |
| `lightmaps` | около 100% углов внутри прямоугольника лайтмапа |
| `objects` | `winding kept`, нет предупреждений о ненайденных файлах |
| `models` | расхождение позы покоя с позициями, записанными в меше, — сантиметры, а не метры (на настоящих данных ещё не сверялось) |
| `portals` | каждый портал ведёт в запечённый мир и нашёл точку прибытия |
| `seams` | сколько вершин сварено и сколько T-стыков закрыто; `+N triangles` — цена в треугольниках |
| `position step` | почти все чанки с шагом 0,125 см; чанки с более грубым шагом — гигантские треугольники моря и гор |

## Сборка для 3DS

Нужен [devkitPro](https://devkitpro.org/wiki/Getting_Started) с группой пакетов `3ds-dev` (devkitARM, libctru, citro3d).

```sh
make
```

Получатся `gothic3ds.3dsx` и `gothic3ds.smdh`. На SD-карте:

```
/3ds/gothic3ds/gothic3ds.3dsx
/3ds/gothic3ds/gothic3ds.smdh
/3ds/gothic3ds/data.pak
```

Запуск через Homebrew Launcher. Управление:

| Кнопка | Действие |
|---|---|
| Circle Pad | движение |
| C-Stick или A/B/X/Y | обзор |
| R | прыжок; на лестнице — отпустить её |
| ZL, ZR | бег |
| SELECT | режим полёта без столкновений и обратно (в полёте L / R — вниз / вверх) |
| Крестовина вниз | время суток на час вперёд |
| Крестовина влево / вправо | дальность прорисовки |
| Крестовина вверх | следующий мир из архива (для отладки) |
| START | выход |

По лестнице поднимаются, идя в неё; спускаются, пятясь на неё сверху. В глубокой воде игрок плывёт, на мелководье идёт медленнее. Порталы между мирами срабатывают при входе в их зону; в режиме полёта они отключены.

При выходе положение, мир, время суток и дальность прорисовки сохраняются в `state.bin` рядом с `data.pak`, следующий запуск продолжает с того же места. Если при запуске держать L, игра начнёт со стартовой точки.

Три переключателя для сравнения на консоли. Их держат, пока программа запускается; что включено, видно на нижнем экране:

| Держать при запуске | Что меняется |
|---|---|
| B | чанки грузятся в основном потоке, как раньше (строка `loader off`) |
| X | регулятор нагрузки выключен: дальность объектов постоянная, 30 к/с не включается (`pacer off`) |
| Y | прежний порядок кадра, как в citro3d: видеочип ждёт, пока процессор выдаст команды (`frames classic`). Задержка управления на кадр меньше, зато кадр стоит «cpu + gpu». Это же запасной путь, если новый порядок поведёт себя неверно |

На нижнем экране:

| Строка | Смысл |
|---|---|
| `frame … avg … worst` | среднее и худшее время между кадрами на экране за 30 кадров |
| `cpu`, `gpu`, `load` | доли кадра 60 к/с: выдача команд процессором, работа видеочипа и то, что из них определяет темп |
| `update … avg … worst` | время подгрузки и игрока в основном потоке; худшее значение — это и есть рывок от подгрузки |
| `loader thread / inline / off`, `job`, `fly` | кто грузит чанки, самая долгая загрузка в фоне за 30 кадров, сколько чанков в пути |
| `detail`, `fps`, `late` | дальность мелких и средних объектов (100% — полная), режим 60 или 30 к/с, сколько кадров из 30 опоздали |
| `frames overlapped / classic`, `pacer` | порядок кадра и состояние регулятора |
| `tris`, `draws`, `chunks`, `blended`, `culled` | треугольники, вызовы отрисовки, чанки в кадре |
| `cmdbuf`, `dropped draws` | заполнение буфера команд GPU; `dropped draws` должно быть 0 |
| `resident`, `pending`, `mesh`, `tex`, `collision`, `linear free` | чанки и память |

Порядок кадра. У citro3d один буфер команд: пока видеочип рисует кадр, процессор не может выдавать команды следующего, поэтому кадр стоит сумму двух времён. Замер на консоли это подтвердил: 28% процессора и 97% видеочипа дали 20,9 мс, то есть 125% от 16,7 мс. Теперь буферов два: процессор записывает команды следующего кадра, пока видеочип рисует предыдущий, и темп задаёт большее из двух времён. Цена — управление отзывается на кадр позже.

Регулятор нагрузки следит за этим временем. Когда кадру нужно больше 90% от 16,7 мс, дальность мелких и средних объектов сокращается (до 35% от заданной), а когда появляется запас, медленно возвращается. Если не хватает и этого, включаются ровные 30 к/с вместо скачков между 60 и 30.

Шаг игры берётся из времени между кадрами на экране. Раньше он измерялся в начале цикла, и раз в 30 кадров печать отчёта на нижний экран сдвигала замер на несколько миллисекунд: один кадр игрок проходил на треть больше обычного, следующий — на треть меньше. Это небольшой рывок дважды в секунду, не связанный с подгрузкой; он же давал «худший кадр» 23–28 мс в прежнем отчёте (у ворот замка 27,7 мс — ровно средние 20,9 плюс те же 6,8). Отчёт теперь пишется по строке за кадр.

Шейдер лежит уже собранным (`platform/3ds/world_shbin.h`). После правки `world.v.pica` его нужно пересобрать, команды — в `scripts/shbin2h.py`.

## Что проверено, а что нет

Замеры на настоящей New 3DS (предыдущая версия, Steam-версия Gothic 1, `WORLD.ZEN`, 953 чанка, дальность 120 м):

| Место | Кадр, мс (средний / худший) | CPU / GPU | Треугольники | Вызовы | Свободно линейной памяти |
|---|---|---|---|---|---|
| Сундук у частокола | 16,7 / 23,5 | 27% / 43% | 26 390 | 672 | 17,5 МБ |
| Ворота замка | 20,9 / 27,7 | 28% / 97% | 60 933 | 685 | 17,6 МБ |
| Река | 16,7 / 23,7 | 23% / 37% | 18 973 | 549 | 18,1 МБ |
| Лагерь с костром | 16,7 / 24,4 | 18% / 56% | 38 677 | 436 | 17,0 МБ |

Мир с объектами держит 60 к/с почти везде; меши занимают около 9 МБ, текстуры 3 МБ, столкновения 5 МБ, буфер команд заполнен на 8–13%, пропущенных вызовов нет. Худший кадр 23–28 мс в этой таблице — не опоздавший кадр, а сдвиг замера из-за печати отчёта (см. выше). Замечены три вещи: редкие рывки, уход видеочипа за 100% в тяжёлых видах (ворота замка) и светлые линии по стыкам полигонов вблизи стен. Эта версия отвечает на все три, но на консоли ещё не запускалась.

Проверено в этой сборке на ПК:

- ПК-часть собирается без предупреждений, все тесты проходят, в том числе под AddressSanitizer и UBSan; тесты фоновой подгрузки — ещё и под ThreadSanitizer.
- Швы. Тест строит стену с T-стыками и вершинами «на волосок рядом» и запекает её двумя способами. По-старому (шаг 0,5 см, без заделки) открытых рёбер 110 м при контуре 36 м, а в 24 видах с 40 см сквозь стену просвечивает фон. По-новому открыт только контур и не просвечивает ни один пиксель. То же на 40 случайно нарезанных и повёрнутых стенах: 1144 T-стыка, все закрыты.
- Фоновая подгрузка даёт тот же мир, что и загрузка на месте: те же чанки, та же память, тот же кадр до пикселя — и без потока, и с ним. Проверены уход от чанков, которые ещё в пути, экран загрузки посреди подгрузки, нехватка видеопамяти, бюджет памяти, смена мира и выход с незаконченной работой.
- Порядок кадра. Бэкенд 3DS (`gfx_c3d.cpp`, без изменений) собирается на ПК с имитацией libctru и citro3d, которая ничего не рисует, а ведёт учёт: какой буфер команд сейчас исполняет видеочип и на какую память он ссылается. Полёт по тестовым мирам с подгрузкой, сменой миров и нехваткой видеопамяти — 846 кадров в каждом из двух порядков, с потоком и без. Нарушений нет: запись в исполняемый буфер, освобождение используемой памяти, отправка кадра занятому видеочипу — всё по нулям. В новом порядке 99% вызовов отрисовки выдаются, пока видеочип занят предыдущим кадром. Это проверка логики по исходникам citro3d, а не запуск на железе.
- Регулятор нагрузки на модели консоли: вид на 105% сводится к ~87% за несколько кадров и остаётся на 60 к/с без качаний; вид, который не помещается и без объектов, переводится на 30 к/с одним переключением.
- Импорт из форматов ZenGin. Тест сам записывает два мира `.ZEN` внутри `.VDF`: меш с BSP-деревом и лайтмапом, меш объекта `.MRM`, модель (`.MDH` + `.MDM` и она же одним `.MDL`) с жёсткой и скиннинговой частью, декаль, лестницу, дверь, триггеры смены уровня, точки прибытия, анимированную воду, текстуры DXT1/DXT3. Затем читает всё обратно и сверяет положение каждой вершины.
- Разбор настоящих файлов игры: тест прогоняет импорт на образцах из набора тестов ZenKit (меш, морф-меш, две модели).
- Шейдер собирается ассемблером picasso.
- Раскладка текстур ETC1 и ETC1A4 сверялась тексель в тексель с декодером эмулятора Azahar в прошлых версиях; этот код с тех пор не менялся.
- Код для 3DS компилируется под ARMv6K (clang) с настоящими заголовками libctru и citro3d без предупреждений; все внешние символы есть в этих библиотеках.
- Рантайм на тестовой сцене из двух миров: полоса препятствий, брод и плавание, подъём и спуск по лестнице, проход через портал туда и обратно, вид под водой, отсечение мелких объектов по расстоянию, сохранение и восстановление положения.

Проверено пользователем на предыдущих версиях (Steam-версия Gothic 1, Azahar и New 3DS):

- `WORLD.ZEN` запекается без ошибок: 106 722 треугольника мира, 7214 объектов из 271 меша, 401 текстура; проверки лайтмапов и порядка граней объектов в норме.
- `.3dsx`, собранный devkitARM через GitHub Actions, работает в Azahar и на консоли: мир, объекты-модели (сундук, костёр), полупрозрачная вода, ходьба по земле.
- Переполнение буфера команд у Старого лагеря исправлено: на консоли `cmdbuf` 8–13%, `dropped draws` 0.

Не проверено:

- **Всё новое в этой версии на консоли и на настоящих данных.** Заделка швов проверена на тестовых стенах, а не на `WORLD.ZEN`: причина линий на фотографиях определена по их виду и воспроизведена на тесте, но сам `WORLD.ZEN` у меня не запекался. Сколько треугольников добавит заделка, покажет строка `seams` отчёта.
- Фоновый поток на консоли: работа с потоками libctru компилируется и сверена с заголовками, но не запускалась. Если поток не создастся, подгрузка идёт без него (строка `loader inline`).
- Новый порядок кадра (запись команд, пока видеочип рисует предыдущий кадр) собран из открытых функций libctru и citro3d и сверен с их исходниками, но на консоли не запускался. Если картинка испортится или программа зависнет, прежний порядок включается кнопкой Y при запуске.
- Точность 24-битных чисел шейдера: расчёт позиции от камеры задуман так, чтобы стыки чанков совпадали до бита; проверить это можно только на консоли (в Azahar шейдер считает в 32 битах).
- Порталы и остальные миры, лестницы, подземные миры, декали на настоящих данных: о них ещё не было отчёта.
- Прозрачность воды: в Gothic 1 она не записана в материале, взято значение на глаз (150 из 255).

Первые шаги на железе описаны в [docs/ROADMAP.md](docs/ROADMAP.md), форматы данных — в [docs/FORMATS.md](docs/FORMATS.md).
